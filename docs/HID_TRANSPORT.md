# CodePC Link vendor HID transport

This branch replaces the Android RFCOMM data path with Bluetooth Classic HID.
The Android phone is the **HID device** and the Linux CodePC is the **HID host**.

The phone does **not** advertise a keyboard or mouse collection. Its report
descriptor uses vendor usage page `0xFF00`, SDP name `CodePC Link Transport`,
and HID subclass `None`. Linux should therefore expose the connection through
`/dev/hidrawN` without generating keyboard input events.

## Pairing model

First pairing remains CodePC-initiated:

1. Open the Android app and keep it in the foreground.
2. Tap **Make phone discoverable (120 s)**.
3. In Cockpit → CodePC Link, click **Scan for phone**.
4. Select the Android phone and click **Pair from CodePC**.
5. Confirm the Android system pairing prompt.
6. Back in the app, choose the bonded CodePC host and tap **Connect HID transport**.

`codepc-link-hid-bt` uses a temporary BlueZ agent scoped to the selected phone.
The adapter is made pairable only during that targeted `Device1.Pair()` call and
is returned to the previous non-pairable state afterwards.

## Data direction

The descriptor contains two fixed 63-byte vendor reports:

- report ID `1`: Android → CodePC commands (HID Input report)
- report ID `2`: CodePC → Android status (HID Output report)

Each report has an 8-byte framing header and up to 55 payload bytes. Multi-report
status messages are chunked and reassembled using sequence, chunk index, and
chunk count fields.

Android can request status immediately. It can also set the server push interval;
the app defaults to five seconds after connecting. The Linux service also starts
with a five-second push interval.

The status JSON deliberately keeps the RFCOMM-era response envelope so the
existing `StatusProtocol` parser remains reusable:

```json
{"schema":1,"ok":true,"op":"status","transport":"hid","status":{}}
```

## Linux commands

Install the branch in a virtual environment or editable checkout, then inspect
HID devices:

```bash
codepc-link-hid find
```

Run the host transport directly for hardware validation:

```bash
sudo codepc-link-hid --verbose serve --interval 5
```

To pin a specific phone after bonding:

```bash
sudo codepc-link-hid --verbose serve --address AA:BB:CC:DD:EE:FF --interval 5
```

Install the system service and Cockpit package:

```bash
sudo ./packaging/install-hid-service.sh
sudo ./packaging/install-cockpit-plugin.sh
```

The Cockpit page can then enable `codepc-link-hid.service`.

## Why hidraw needs privilege for the first prototype

Bluetooth HID devices are created dynamically by the kernel and the resulting
`/dev/hidrawN` node is commonly root-owned. The prototype systemd service runs
as root, has no ambient capabilities, and uses the real `/dev` tree so it can
open the dynamic hidraw node. After hardware validation this should be tightened
with a dedicated udev rule and static service account/group.

## Android lifecycle caveat

Android's `BluetoothHidDevice` application registration exists only while the
app is foreground. Keep CodePC Link HID open during discovery, pairing, and the
HID connection. Registering an Android HID Device application also temporarily
disables Android's HID Host profile for the lifetime of the registration; it
does not replace the Android on-screen IME, and this CodePC descriptor never
sends keyboard usages to Linux.

## Hardware validation checklist

- Linux discovers the phone while the Android app is foreground and discoverable.
- Pairing is started from Cockpit, not from the phone.
- The bond persists and the adapter returns to non-pairable state.
- Connecting from Android creates a `CodePC Link Transport` hidraw node.
- No keyboard `/dev/input` key events are generated by CodePC Link reports.
- `Request status now` returns schema-1 JSON.
- Five-second auto status updates arrive continuously.
- Setting auto status off stops periodic pushes while manual requests still work.
- Disconnect/reconnect works five times without deleting the bond.
